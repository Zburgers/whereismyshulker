# Where Is My Shulker — Minecraft 26.2 Implementation Plan

Status: ready for one implementation agent  
Companion spec: `docs/26.2-migration-spec.md`  
Inspected code base: `PLAN_BASE_SHA=29ec55b5d8c6da614764d33da95378ec42a0d99b`  
Target: Minecraft `26.2`, Fabric, Java `25`

This plan is intentionally mechanical. Work in order. Do not skip a verification checkpoint because the next phase assumes the previous one is known-good.

## 0. Delivery contract

Deliver one coherent PR/branch that ports the existing mod to Minecraft 26.2 without turning it into a server mod.

Preserve:

- client-only operation on arbitrary servers;
- existing singleplayer and multiplayer CSV locations;
- existing row schema and history readability;
- `/shulker`, `/shulker <page>`, `/shulker clear`, `/shulker clearall`;
- named/color/dimension/distance output;
- placement recorded only after successful placement.

Change deliberately:

- Yarn/obfuscated toolchain → native 26.2 official names;
- Java 21 → 25;
- old break Mixin → Fabric `ClientPlayerBlockBreakEvents.AFTER`;
- fuzzy command argument → explicit Brigadier branches;
- destructive client commands → attended commands;
- deletion key → dimension + position;
- custom-name parsing → last-column-safe split;
- translation-key color parsing → `ShulkerBoxBlock.getColor()`;
- client shutdown-only cleanup → play disconnect cleanup;
- remove empty main entrypoint/mixin scaffolding.

Use the target official APIs exposed by 26.2. Expected shape:

### F4 — preserve multiplayer storage location semantics

Continue sanitizing the current server address and storing at:

### F5 — resolve singleplayer path directly to the world's data directory

Prefer the integrated server's official level-path API with `LevelResource.DATA`, then append `shulker_boxes.csv`.

The resulting path must still be:

`<world>/data/shulker_boxes.csv`

Retain a safe fallback under `.minecraft/.whereismyshulker/default/` if a world/save path cannot be resolved.

### F6 — centralize dimension id conversion

Add a small private helper, e.g.:

```java
private static String getDimensionId(Level level) { ... }
```

Use the level's dimension resource key/identifier and return the same string shape as historical files, e.g. `minecraft:overworld`, `minecraft:the_nether`, `minecraft:the_end`.

The exact 26.2 chain should be read from the compiler/source (expected to be based on `level.dimension()` and its identifier/location). This helper prevents command, placement and removal code from inventing different formats.

If command code needs it, make it package-private static rather than duplicating logic.

### F7 — replace translation-key color parsing

Delete `getShulkerBoxColor(Block)`'s translation-key parsing and the `capitalize` helper.

For a `ShulkerBoxBlock`, use its 26.2 `getColor()` API. Preserve storage/display strings:

- undyed/null color → `""`;
- dyed color → lowercase serialized color name such as `"light_blue"` or normalize once to the display form expected by the command.

Choose one representation deliberately. **Preferred compatibility path:** keep the persisted values exactly as the current user-visible values (`"Light Blue"`, `"Red"`, etc.) so historical and new rows display identically. Convert the dye color's stable name to title-case in one helper rather than parsing block translation keys.

### F8 — make removal dimension-aware

```java

```

to either:

```java

```

or:

```java

```

Prefer the `Level` form at the event boundary and compute the canonical id in the tracker.

Remove only rows satisfying both:

```text

```

### F9 — keep storage I/O behavior stable

Do not redesign file locking, async I/O, schema versioning, or storage format. Preserve load-on-join and save-on-mutation behavior.

```text

├── <page: integer >= 1>
├── clear
├── clearall
```
