# Where Is My Shulker — Minecraft 26.2 Migration Spec

Status: implementation-ready migration specification  
Research date: 2026-08-29  
Repository: `Zburgers/whereismyshulker`  
Plan base: `PLAN_BASE_SHA=29ec55b5d8c6da614764d33da95378ec42a0d99b`

## 1. Goal

Port **Where Is My Shulker** from Minecraft **1.21.11** to **Minecraft 26.2** on Fabric while preserving the mod's defining deployment model: it remains a **client-only mod that works on singleplayer and on multiplayer servers without requiring a server-side mod**.

The port is successful when a Fabric 26.2 client can launch the built jar, track player-placed shulker boxes, remove player-broken shulker boxes, persist and reload existing CSV history, expose the `/shulker` command UX, and switch cleanly between worlds/servers without stale state. The implementation should also remove obsolete compatibility scaffolding and replace low-level hooks with stable Fabric APIs where 26.2 provides them.

This is a compatibility port plus narrowly-scoped hardening of code paths that have to be touched anyway. It is **not** a redesign into a server-authoritative tracker.

## 3. Mental model for a non-Java developer

A Fabric mod is ordinary Java code loaded into the Minecraft process, plus metadata telling Fabric which classes to instantiate and which Minecraft classes should be modified.

For this mod there are four concepts worth knowing:

1. **Entrypoint** — the Java class Fabric calls when the client starts. Here that is `WhereismyshulkerClient`.
2. **Fabric events** — stable callbacks exposed by Fabric API, similar to framework hooks such as `onConnect`, `onDisconnect`, or `afterBlockBreak`.
3. **Mixin** — bytecode-level patching of a Minecraft class. A Mixin is powerful but is tightly coupled to a target class/method signature, so it is a higher-maintenance integration point than a public Fabric event.
4. **Loom/Gradle** — the build toolchain. Loom wires Minecraft, Fabric, mappings/remapping when applicable, run configurations, Mixin processing, and packaging into Gradle.

The mod does not have a custom block, entity, screen, renderer, packet protocol, database, or server component. That keeps this port unusually contained.

## 4. Current architecture

### 4.1 Runtime modules

The source tree is effectively five pieces:

- `src/client/java/org/mcsebi/whereismyshulker/client/WhereismyshulkerClient.java`
  - real client entrypoint;
  - registers lifecycle/network callbacks;
  - registers `/shulker`;
  - renders command output, pagination, distance and dimension information.
- `src/client/java/org/mcsebi/whereismyshulker/client/ShulkerBoxTracker.java`
  - singleton in-memory store;
  - determines the per-world/per-server CSV path;
  - reads and rewrites the CSV file;
  - records placement and removal.
- `src/client/java/org/mcsebi/whereismyshulker/client/ShulkerBoxData.java`
  - immutable record-like model containing position, dimension, color, timestamp and custom name;
  - serializes/deserializes one CSV row.
- `src/client/java/org/mcsebi/whereismyshulker/client/mixin/BlockItemMixin.java`
  - injects at `BlockItem.place` HEAD and RETURN;
  - captures the source stack custom name before placement mutates the stack;
  - after successful placement, verifies a shulker box exists at the placement position and records it.
- `src/client/java/org/mcsebi/whereismyshulker/client/mixin/ClientPlayerInteractionManagerMixin.java`
  - injects around the client's block-break method;
  - remembers whether the pre-break block was a shulker;
  - after a successful client break, removes the tracked position.

There is also dead scaffolding:

- `src/main/java/org/mcsebi/whereismyshulker/Whereismyshulker.java` is a `ModInitializer` whose `onInitialize()` is empty.
- `src/main/resources/whereismyshulker.mixins.json` contains no mixins.
- `fabric.mod.json` nevertheless declares both the empty main entrypoint and empty main mixin config.
- `WhereismyshulkerClient` registers an empty `CLIENT_STARTED` callback.

These should be removed as part of the port.

### 4.2 Placement flow

Current flow:

`player uses shulker item`  
→ Minecraft calls `BlockItem.place(...)`  
→ Mixin at HEAD captures the stack custom name into a `ThreadLocal`  
→ vanilla placement executes  
→ Mixin at RETURN checks that placement succeeded and that the resulting block is a shulker  
→ tracker stores `(position, dimension, color, timestamp, customName)`  
→ tracker rewrites the CSV file.

The double injection is deliberate. Capturing only after placement can lose information from the source `ItemStack`; recording only before placement would create false records for failed placements.

**Decision:** keep this one Mixin for the 26.2 port, but migrate its class/method types to official unobfuscated names and revalidate the injection signature at compile/runtime.

### 4.3 Break flow

Current flow:

`player breaks block`  
→ Mixin at the client interaction manager method HEAD checks the pre-break block state  
→ vanilla break executes  
→ Mixin at RETURN checks success  
→ tracker removes every record with the same `BlockPos`  
→ tracker rewrites the CSV file.

Fabric now exposes `ClientPlayerBlockBreakEvents.AFTER`, explicitly described as the client-side callback after a block is successfully broken.

**Decision:** replace `ClientPlayerInteractionManagerMixin` with `ClientPlayerBlockBreakEvents.AFTER`. This reduces version-sensitive bytecode coupling while retaining the client-only product model.

### 4.4 Persistence flow

The tracker keeps an in-memory `List<ShulkerBoxData>` and rewrites the whole CSV file on each mutation.

Singleplayer location today:

`<world>/data/shulker_boxes.csv`

Multiplayer location today:

`.minecraft/.whereismyshulker/<sanitized-server-address>/shulker_boxes.csv`

The multiplayer path is based on the server entry address. The singleplayer path is resolved from the integrated server when available.

**Invariant:** do not move or rename existing data files during the 26.2 port. Existing histories should load without a migration step.

### 4.5 Command flow

`/shulker` defaults to page 1. The current command uses one string argument, then manually decides whether the string is a page number or one of several reset/clear spellings. It emits clickable command text for pagination and a coordinate component that suggests a teleport command.

Documented user-facing behavior is:

- `/shulker`
- `/shulker <page>`
- `/shulker clear`
- `/shulker clearall`

The implementation also accepts reset/prune-like strings through prefix matching.

**Decision:** move to an explicit Brigadier tree: an integer `page` argument and literal destructive subcommands. Preserve documented commands; preserving existing reset/prune aliases is acceptable if implemented explicitly rather than through fuzzy prefix parsing.

## 5. The major migration landmarks

### 5.1 Landmark A — 1.21.11 is the end of the old Yarn/obfuscation era

This repository is sitting exactly on the old side of the largest recent Fabric toolchain boundary.

Minecraft 1.21.11 is the last release in this lineage where the traditional obfuscated-game + mappings workflow applies. Fabric documents that for 26.1 and newer, mods coming from Yarn must first migrate to Mojang's official names; 26.1 itself is unobfuscated, so target builds no longer carry a Yarn mapping dependency.

Implications for this repository:

- all `net.minecraft.*` imports change from Yarn vocabulary to Mojang/official vocabulary;
- Mixin target signatures must be reviewed manually even if a mapping migration tool is used;
- code review must distinguish automatic name migration from actual vanilla/API behavior changes.

For this repository, the safe migration sequence is conceptual rather than release-based:

1. while still on Minecraft 1.21.11, translate the source set from Yarn names to Mojang mappings;
2. then change the target toolchain/build to 26.2 and fix true version/API breakages.

There is no need to publish or maintain an intermediate 26.1 version.

### 5.2 Landmark B — 26.1 rebuilds the Fabric development model

Fabric describes 26.1 as its largest single-release tooling/API change. For this repository the load-bearing changes are:

- `fabric-loom` / remapping-era usage → `net.fabricmc.fabric-loom` for non-obfuscated Minecraft;
- remove the Yarn `mappings` dependency at the 26.2 target;
- `modImplementation` → standard `implementation`;
- Java 21 → **Java 25**;
- remapping assumptions disappear for target jars;
- Fabric API names were aligned with Mojang names.

Two specific Fabric API renames directly hit this code:

- `ClientCommandManager` → `ClientCommands`;
- `FabricClientCommandSource.getWorld()` → `getLevel()`.

Fabric explicitly warns that these Fabric API renames are **not** handled by mappings migration tools.

The repository's `fabric.mod.json` also currently depends on the legacy mod id `"fabric"`. Fabric removed that id in 26.1; the dependency must be `"fabric-api"`.

### 5.3 Landmark C — 26.2 itself is a smaller delta for this mod

26.2's most visible platform change is the experimental Vulkan render backend and the direction away from raw OpenGL. This mod has **no rendering code and makes no raw OpenGL calls**, so Vulkan is not a migration blocker.

26.2's registration/data-generation changes also do not materially affect this mod because it registers no blocks, items, entities, recipes or data generators.

The relevant 26.2 Fabric change is **attended client commands**. Fabric API 0.152.0 added `.requires(FabricClientCommandSource::attended)` so a server-provided clickable text component cannot silently execute a sensitive client-side command without user intent.

`/shulker clear` and `/shulker clearall` mutate local persistent data, so they should be protected by the attended predicate. Pagination is non-destructive and does not need that gate.

## 6. Target architecture

The target remains client-only but uses Fabric APIs before Mixins whenever semantics allow it.

### Target runtime flow

`WhereismyshulkerClient`

- on play JOIN → resolve/load the world/server CSV;
- on play DISCONNECT → clear in-memory state and file path;
- on client block-break AFTER event → if the pre-break state is a shulker, remove the record for that **dimension + position**;
- register explicit `/shulker` command branches;
- retain client-stop cleanup as defensive cleanup if useful, but DISCONNECT is the session boundary that matters.

`BlockItemMixin`

- remains the only Mixin;
- capture custom name at `BlockItem.place` HEAD;
- after successful return, resolve resulting block/position and record placement;
- always clear the `ThreadLocal` in `finally`.

`ShulkerBoxTracker`

- preserve the current storage locations and on-disk row shape;
- use official 26.2 Minecraft types;
- derive the dimension from the level's resource key/identifier;
- use `ShulkerBoxBlock.getColor()` instead of parsing a translation key;
- remove by `(dimension, BlockPos)`, not `BlockPos` alone.

`ShulkerBoxData`

- preserve the current seven-column row format;
- parse with `split(",", 7)` so a custom name containing commas remains in the final field instead of corrupting row loading.

### Dead code removed

Remove:

- empty main `ModInitializer`;
- empty main Mixin config;
- empty `CLIENT_STARTED` registration;
- `ClientPlayerInteractionManagerMixin` after the Fabric client break event is wired.

The resulting mod has one client entrypoint and one client Mixin config.

## 7. Migration hardening included in scope

These are intentionally included because they are tiny, correctness-critical, and lie directly on touched migration boundaries:

### Dimension-safe removals

Current `onShulkerBoxBroken(BlockPos)` removes every record at the same XYZ regardless of dimension. A shulker at `(100, 64, 100)` in the Overworld and another at the same coordinates in the Nether can therefore be deleted together from history.

The 26.2 callback provides the client level, so removal must compare both dimension id and position.

### Comma-safe custom names

Current `fromCsv` uses `split(",")`, rejects rows with more than seven parts, and therefore loses a record after restart if a custom shulker name contains a comma.

Use `split(",", 7)`. This is intentionally not a wholesale CSV-format rewrite: it fixes the current schema while preserving compatibility and adding no dependency.

### Direct color API

Current color detection parses a translation key such as `block.minecraft.red_shulker_box`.

26.2's unobfuscated `ShulkerBoxBlock` exposes `getColor()`. Use that API; map null to the existing undyed representation (`""`) and use the dye color's stable serialized/name representation for dyed boxes.

### Proper disconnect cleanup

Current state is cleared when the whole client stops, not when the player disconnects from one server/world and joins another in the same Minecraft process.

Register `ClientPlayConnectionEvents.DISCONNECT` and call `onWorldUnload()` there. This is required to prevent stale in-memory state or file paths crossing sessions.

### Explicit and attended destructive commands

Replace fuzzy string dispatch with Brigadier literals and an integer page argument. Apply `.requires(FabricClientCommandSource::attended)` to all local-data-destructive command branches and any preserved aliases.

## 8. Strongest rejected alternative

### Alternative: make tracking server-authoritative

A server-side implementation could observe more authoritative events and maintain canonical shulker positions. It could potentially track explosions, other players, command-driven changes and other mutations that a client-only intent tracker misses. It could store state in server `SavedData` and sync results to clients.

That architecture is stronger for correctness but is rejected for this migration because it changes the product contract: multiplayer servers would have to install the mod or protocol support. The current mod's main value is that a player can install it locally and use it on arbitrary Fabric-compatible/vanilla servers. A server rewrite also introduces networking, server persistence, permissions and compatibility concerns far beyond a version port.

If authoritative global tracking becomes a future product goal, treat it as a separate v2 design rather than smuggling it into the 26.2 migration.

## 9. Design invariants

The implementation must preserve all of these:

1. **Client-only deployment:** a multiplayer server does not need this mod installed.
2. **Existing history compatibility:** existing `shulker_boxes.csv` files remain readable in place.
3. **No false placement on vanilla placement failure:** a record is created only after placement succeeds.
4. **Custom name capture:** a successfully placed named shulker retains the name from its source stack.
5. **Dimension identity:** a tracked record is identified for deletion by both dimension and block position.
6. **Player-break semantics:** only client-observed player breaks are removed; the port does not claim to track explosions/pistons/other players.
7. **Session isolation:** disconnecting from world/server A before joining B cannot leak A's records into B.
8. **No raw rendering dependency:** the port introduces no OpenGL/Vulkan-specific code.
9. **One Mixin maximum in the target design:** placement remains a Mixin; block breaking uses Fabric's public event.
10. **Destructive command intent:** local history deletion cannot be triggered through an unattended client command path.

## 11. Acceptance criteria

The port is accepted only if all of the following are true:

- The repository builds successfully for Minecraft 26.2 using Java 25.
- A clean Fabric 26.2 client launches the built mod jar with Fabric API and no Mixin errors.
- The mod remains client-only and works when joining a server that does not have Where Is My Shulker installed.
- `/shulker` displays tracked boxes with names/colors, coordinates, dimensions/distance, and pagination.
- Placing a shulker records it only when placement succeeds.
- A custom name containing a comma is still present after disconnect/restart and reload.
- Breaking a tracked shulker removes it; a same-XYZ record in another dimension remains.
- Disconnecting and joining a second server/world in the same client does not leak the first session's records.
- Existing pre-port CSV data is read from the same on-disk location.
- `/shulker clear` and `/shulker clearall` remain usable when intentionally invoked and are guarded as attended client commands.
- `ClientPlayerInteractionManagerMixin`, the empty main initializer, and the empty main Mixin config are gone.
- Only the placement Mixin remains.
- README dependency/runtime notes are accurate for 26.2 after implementation.

## 12. Risks and edge cases

### Client prediction is not server authority

A client-side successful-break/placement signal can still differ from final server truth in unusual protection, rollback or packet-race scenarios. Eliminating this class of mismatch requires a more authoritative server/network design, which is out of scope.

### Non-player mutations are still not tracked

Explosions, piston movement, commands, another player's break, and other mutations are not made authoritative by this port. README already communicates part of this limitation; update wording if necessary, but do not broaden implementation scope.

### Synchronous full-file rewrites

Every mutation rewrites the complete CSV on the client thread. For normal personal-history sizes this is likely acceptable and matches current behavior, but very large histories can produce stalls. Storage redesign is out of scope.

### CSV is still a deliberately simple schema

`split(",", 7)` fixes commas in the last field without changing historical rows. It does not implement quoting/escaping for a future field that might itself need arbitrary separators. A future storage-version migration should use a real structured format or proper CSV library.

### Server address identity

The same physical server reached through different DNS names/addresses can produce separate history folders. Preserve current behavior in this port.

## 13. Unverified assumptions the implementation agent must close

These details are intentionally compiler/runtime-verified rather than guessed into correctness:

- exact 26.2 official method spelling for the placement context's final placement position and level access;
- exact 26.2 success predicate on `InteractionResult` used by `BlockItem.place`;
- exact official helper used to obtain the integrated server's `LevelResource.DATA` path;
- exact dye-color string accessor used to preserve the current lowercase color strings.

The design does **not** depend on one particular spelling. The implementation agent should inspect the 26.2 source/Javadocs available through Loom, choose the official method, and keep the behavioral invariants above.

## 14. Out of scope

- server-side installation or networking protocol;
- globally authoritative shulker tracking;
- tracking explosions, pistons, commands, other players or arbitrary world edits;
- renderer/HUD/waypoint additions;
- converting CSV to JSON/NBT/database storage;
- configuration UI;
- multi-loader support such as NeoForge;
- backporting the new architecture to 1.21.11;
- publishing to Modrinth/CurseForge;
- broad command redesign beyond making the existing surface explicit and safe;
- performance redesign of file I/O.

## 16. Shipyard judgment

### Approach and why

Perform the migration as one coherent PR, but in gated phases: first translate the existing 1.21.11 Yarn source to Mojang names while still on 1.21.11; then switch the build to native unobfuscated 26.2; then modernize the client hooks and commands; then harden persistence/session behavior; finally run the build and gameplay smoke matrix. This sequence separates name churn from real API/behavior churn and makes failures much easier to diagnose.

### Strongest alternative and why rejected

The strongest alternative is a server-authoritative rewrite. It yields better world truth but destroys the zero-server-install property and multiplies the migration surface. It is deliberately rejected for this PR.

### Risks worth protecting

The one remaining Mixin is the highest compatibility risk; historical CSV compatibility is the highest data risk; session boundary and dimension-aware deletion are the highest correctness risks. The execution plan must produce evidence for each.

### Docs requiring updates

`README.md` after implementation.

### Visual-debug obligations

None. There is no custom rendering/UI surface in scope; command chat output is covered by manual runtime smoke tests.

### Pre-gate checkpoint

`running preview`: before final gate/review, run the 26.2 client and execute the complete smoke matrix in a real world and a multiplayer connection.

### Ship profile

`START standard / BUILD standard / GATE frontier / effort high / process full`
