**Status:** implementation-ready / research refreshed

**Repository:** `Zburgers/whereismyshulker`

This document is the architecture and compatibility contract for porting **Where Is My Shulker** from Minecraft **1.21.11** to **Minecraft 26.2** on Fabric. The companion `26.2-implementation-plan.md` turns this contract into byte-sized execution steps. `26.2-research-audit.md` records source-of-truth evidence and confidence levels. `26.2-shipyard-handoff.md` is the execution handoff for a single implementation agent.

---

## 1. Executive decision

Port the existing mod in place to Minecraft 26.2 and keep its defining product contract:

> **Where Is My Shulker remains a client-only mod. A multiplayer server must not need this mod installed.**

The port is a compatibility migration plus small correctness fixes on code paths that must already change for 26.2. It is **not** a rewrite into a server-authoritative tracker and it is **not** a feature release.

The target architecture has:

- one client entrypoint;
- one remaining Mixin, for successful shulker placement + pre-placement custom-name capture;
- Fabric API events for block-break and connection lifecycle;
- Fabric client command v2 for `/shulker`;
- the existing CSV storage locations and row shape;
- no custom networking, GUI, renderer, registry objects, or server-side code.

The port is complete only when the built jar launches on 26.2, all mandatory smoke tests pass, and historical CSV data remains readable in place.

## 3. Current system: what the mod actually does

This is a small client mod. Understanding its runtime shape is more valuable than treating it like a generic Minecraft project.

### 3.1 Runtime modules

#### `WhereismyshulkerClient`

Client entrypoint. It currently:

- registers a JOIN callback and loads the active CSV;
- clears tracker state only when the whole client stops;
- registers `/shulker`;
- formats pagination, dimensions, direction, distance, colors, coordinates, hover text, and clickable navigation.

Problems relevant to 26.2:

- Yarn/Fabric API vocabulary is old (`ClientCommandManager`, `Text`, `Formatting`, `getWorld()`);
- command parsing is a single string with fuzzy `reset` / `prune` / `clear` prefix logic;
- destructive client commands are not attended;
- there is no normal play-session DISCONNECT cleanup;
- an empty `CLIENT_STARTED` callback exists.

#### `ShulkerBoxTracker`

Singleton mutable store and persistence boundary. It currently:

- owns an in-memory `List<ShulkerBoxData>`;
- resolves a CSV path on world/server load;
- reads CSV into memory;
- rewrites the full file after each placement/removal/reset;
- stores multiplayer history under a sanitized server address;
- stores singleplayer history under the world's `data` directory.

Important current bugs/fragility:

- block removal matches `BlockPos` only, so matching XYZ in different dimensions collide;
- shulker color is derived by parsing a translation key;
- lifecycle cleanup occurs at client shutdown, not normal server/world disconnect;
- many imports/member names cross the Yarn → official-name boundary.

#### `ShulkerBoxData`

Small immutable-ish row object with:

- `BlockPos position`;
- dimension id string;
- color string;
- timestamp;
- custom name.

On-disk row shape:

```text
x,y,z,dimension,color,timestamp,customName
```

The parser currently uses `split(",")`. A custom name containing a comma creates more than seven tokens and the row is silently rejected on the next load.

#### `BlockItemMixin`

The placement hook. It injects into `BlockItem.place` twice:

1. at HEAD, snapshot the source stack's custom name before vanilla placement mutates/decrements it;
2. at RETURN, record only if vanilla placement succeeded and the resulting block is a shulker.

A `ThreadLocal<String>` bridges the two injections and is cleared in `finally`.

This semantic pattern is valid and should remain the one low-level hook in the 26.2 port.

#### `ClientPlayerInteractionManagerMixin`

The current break hook injects around client block breaking, remembers whether the old block was a shulker, then removes it after a successful break.

This Mixin is obsolete for the target because Fabric now exposes a client-side AFTER block-break event with the pre-break `BlockState`.

### 3.2 Dead main-side scaffolding

The repository also contains:

- an empty `ModInitializer` at `src/main/java/org/mcsebi/whereismyshulker/Whereismyshulker.java`;
- an empty main Mixin config;
- corresponding declarations in `fabric.mod.json`.

They add no behavior and should be removed. Target metadata should expose only the real client entrypoint and client Mixin config.

## 4. The migration boundary: 1.21.11 → 26.2

### 4.1 The largest change is 26.1, not 26.2

This repository sits exactly across Fabric's recent obfuscation/tooling boundary.

For 1.21.11 and older:

- Minecraft is developed against mapped names;
- this repository uses Yarn;
- Loom uses the remapping-era model;
- dependencies use `modImplementation` in this project.

For 26.1+ / 26.2:

- Minecraft is unobfuscated for this workflow;
- target source uses Mojang/official names directly;
- target build has **no Yarn mappings dependency**;
- Loom plugin id is `net.fabricmc.fabric-loom` for non-obfuscated Minecraft;
- normal `implementation` dependencies are used;
- Java 25 is required by the target ecosystem.

### 4.2 Required migration sequencing

Do not jump straight from Yarn names to guessed 26.2 code.

The safe sequence is:

1. with the project still on Minecraft 1.21.11, migrate source vocabulary from Yarn to Mojang mappings using Loom's `migrateMappings` task;
2. inspect the diff, especially both Mixins;
3. move the build/toolchain to 26.2;
4. fix true 26.2 API/semantic differences using the official target sources and Fabric API.

This separates **name migration** from **behavioral migration**, which makes compiler failures and review much easier to reason about.

### 4.3 Fabric API rename hits specific to this mod

Known target vocabulary:

- `ClientCommandManager` → `ClientCommands`;
- `FabricClientCommandSource.getWorld()` → `getLevel()`;
- Yarn text types → Mojang `Component`, `MutableComponent`, `ChatFormatting`;
- Yarn world/client types → official `Level`, `ClientLevel`, `Minecraft`, `BlockPos`, etc.

A mappings migration tool does not guarantee all Fabric API names will be rewritten; compile against the real target API.

## 5. Exact 26.2 integration contracts

The following are implementation decisions, not suggestions.

### 5.1 Block breaking: delete the break Mixin

Use:

```java
net.fabricmc.fabric.api.event.client.player.ClientPlayerBlockBreakEvents.AFTER
```

The verified callback shape is:

```java
void afterBlockBreak(
    ClientLevel level,
    LocalPlayer player,
    BlockPos pos,
    BlockState state
)
```

Fabric documents `state` as the block state **before** the block was successfully broken.

Target behavior:

```java
ClientPlayerBlockBreakEvents.AFTER.register((level, player, pos, state) -> {
    if (state.getBlock() instanceof ShulkerBoxBlock) {
        ShulkerBoxTracker.getInstance().onShulkerBoxBroken(pos, level);
    }
});
```

Then:

- delete `ClientPlayerInteractionManagerMixin.java`;
- remove it from `whereismyshulker.client.mixins.json`;
- do not replace it with another Mixin.

### 5.2 Connection lifecycle: JOIN + DISCONNECT are the session boundary

Use `ClientPlayConnectionEvents`.

Verified target callbacks:

- `JOIN`: `(ClientPacketListener listener, PacketSender sender, Minecraft client)`;
- `DISCONNECT`: `(ClientPacketListener listener, Minecraft client)`.

Contract:

```text
JOIN       -> resolve active storage identity + load CSV
DISCONNECT -> clear in-memory rows + clear csvFilePath
```

Client shutdown cleanup may remain as a redundant safety net, but it is not a substitute for DISCONNECT.

### 5.3 Client commands

Use Fabric client command v2 with:

- `ClientCommandRegistrationCallback`;
- `ClientCommands.literal(...)`;
- `ClientCommands.argument(...)`;
- `FabricClientCommandSource.getLevel()`;
- `sendFeedback(Component)` / `sendError(Component)`.

Target command tree:

```text
shulker
├── <page: integer >= 1>
├── clear
├── clearall
├── reset      (optional compatibility alias)
├── resetall   (optional compatibility alias)
├── prune      (optional compatibility alias)
└── pruneall   (optional compatibility alias)
```

Rules:

- `/shulker` shows page 1;
- `<page>` is an actual Brigadier integer, not a string parser;
- documented `clear` and `clearall` remain;
- aliases, if kept, are explicit literals only;
- every destructive literal has:

```java
.requires(FabricClientCommandSource::attended)
```

Fabric's `attended()` contract is specifically designed to prevent destructive/privileged client commands from being executed through server-provided clickable text without direct user intent.

Do **not** gate root/page navigation as attended. Pagination emitted by this mod should stay clickable.

### 5.4 Text components

Preserve the current command UX using the official 26.2 text API:

- `Component` / `MutableComponent`;
- `ChatFormatting`;
- `ClickEvent.RunCommand` for pagination;
- `ClickEvent.SuggestCommand` for coordinate teleport suggestions;
- `HoverEvent.ShowText`;
- style mutation through the current component/style API.

The coordinate click must continue to **suggest** `/tp @s x y z`; it must never silently execute teleportation.

### 5.5 Placement Mixin: keep exactly one Mixin

Target classes/concepts:

- `net.minecraft.world.item.BlockItem`;
- `net.minecraft.world.item.context.BlockPlaceContext`;
- `net.minecraft.world.InteractionResult`;
- `net.minecraft.world.level.Level`;
- `net.minecraft.world.level.block.ShulkerBoxBlock`;
- `net.minecraft.core.BlockPos`;
- `net.minecraft.world.level.block.state.BlockState`.

Target method contract:

```text
BlockItem.place(BlockPlaceContext) -> InteractionResult
```

HEAD injection:

1. return unless `context.getLevel().isClientSide()`;
2. cast `this` to `BlockItem`;
3. return unless `getBlock()` is a `ShulkerBoxBlock`;
4. read `context.getItemInHand().getCustomName()`;
5. snapshot `Component.getString()` or `""` into the ThreadLocal.

RETURN injection:

1. wrap body in `try/finally` so the ThreadLocal is always removed;
2. require a non-null return value whose `consumesAction()` is true;
3. require client side;
4. require the item block to be a shulker;
5. resolve the placement position from the 26.2 context (`getClickedPos()` in current official vocabulary; compile/runtime validate descriptor);
6. read the resulting `BlockState`;
7. record only if the resulting block is a `ShulkerBoxBlock`;
8. pass the captured custom name to the tracker.

Mixin config keeps `defaultRequire: 1`. Do **not** reduce injection strictness to hide a failed target.

Runtime launch validation is mandatory because a Mixin can compile while still targeting the wrong runtime descriptor.

### 5.6 Shulker color

Do not parse translation keys.

Use:

```text
ShulkerBoxBlock.getColor() -> nullable DyeColor
```

Storage/display compatibility:

- null / undyed → `""`;
- dyed → derive a human-readable value from the dye's stable serialized name, e.g. `light_blue` → `Light Blue`.

Historical files may already contain title-cased color strings. New rows should retain the same user-facing convention so old/new rows display consistently.

### 5.7 Canonical dimension identity

Use one helper everywhere. Target official shape:

```java
static String dimensionId(Level level) {
    return level.dimension().identifier().toString();
}
```

Expected values remain:

- `minecraft:overworld`;
- `minecraft:the_nether`;
- `minecraft:the_end`.

The command renderer, placement path, and removal path must use the same canonical representation.

## 6. Persistence compatibility contract

### 6.1 Existing paths are part of the product contract

Do not migrate or rename user history in this port.

Singleplayer:

```text
<world>/data/shulker_boxes.csv
```

Multiplayer:

```text
.minecraft/.whereismyshulker/<sanitized-server-address>/shulker_boxes.csv
```

Fallback:

```text
.minecraft/.whereismyshulker/default/shulker_boxes.csv
```

### 6.2 Target 26.2 path resolution

Use official client/server names, preserving path semantics.

Multiplayer concept:

```java
Minecraft client = Minecraft.getInstance();
ServerData serverData = client.getCurrentServer();
// use serverData.ip, apply the existing sanitization, and resolve under client.gameDirectory
```

Singleplayer concept:

```java
IntegratedServer server = client.getSingleplayerServer();
Path csv = server.getWorldPath(LevelResource.DATA).resolve("shulker_boxes.csv");
```

Do not change the sanitizer during this compatibility port unless a verified target API requires it. Changing a sanitizer would strand existing multiplayer history under a different directory name.

### 6.3 CSV row compatibility

Keep the existing six/seven-column compatibility behavior but fix comma handling in the final field:

```java
String[] parts = csvLine.split(",", 7);
```

Continue accepting:

- six-column historical rows with no custom name;
- seven-column rows with a custom-name field.

Normalize a null custom name to `""` in memory.

This is deliberately **not** a general CSV escaping rewrite. The custom name is the final field, so a split limit fixes the known compatibility bug without introducing a schema migration or dependency.

### 6.4 I/O behavior stays simple

Preserve:

- load on JOIN;
- full file rewrite on mutation;
- local filesystem only;
- no async persistence;
- no database;
- no locking/schema framework.

The data volume is tiny and the port should not introduce unrelated persistence complexity.

## 7. Correctness fixes included in migration scope

These are required because they are small, high-value, and directly touch migrating code.

### 7.1 Dimension-safe removal

Current bug:

```text
Overworld (100,64,100)
Nether    (100,64,100)
```

Breaking either currently removes both because deletion compares only `BlockPos`.

Target removal identity:

```text
dimension id + BlockPos
```

API shape:

```java
onShulkerBoxBroken(BlockPos pos, Level level)
```

Then remove only rows whose position **and** canonical dimension id match.

### 7.2 Comma-safe custom names

A name such as:

```text
Ops, Red
```

must survive disconnect/reload. This is a mandatory regression test.

### 7.3 Session isolation

World/server A data must not remain in memory after disconnect when the player joins world/server B without restarting Minecraft.

`ClientPlayConnectionEvents.DISCONNECT` is the required fix.

### 7.4 Direct color API

`ShulkerBoxBlock.getColor()` replaces translation-key string parsing.

### 7.5 Explicit destructive commands

Fuzzy prefix parsing is removed. Destructive actions are explicit Brigadier literals and require attended execution.

## 9. Design invariants

The implementation agent must protect all of these.

1. **Client-only deployment.** No server installation is required.
2. **Historical storage compatibility.** Existing paths and row shape remain readable.
3. **No false placement.** Failed vanilla placement never creates a row.
4. **Custom-name preservation.** A named source shulker keeps its name in history.
5. **Correct dimension identity.** Same XYZ in different dimensions are independent rows.
6. **Session isolation.** Disconnecting A before joining B clears A's in-memory/path state.
7. **Intentional destructive commands.** Clear operations require attended command execution.
8. **No hidden teleport execution.** Coordinate clicks only suggest a command.
9. **Stable UX.** `/shulker`, page navigation, name/color/dimension/distance display remain available.
10. **Minimal low-level patching.** Only the placement Mixin remains; Fabric API is preferred where semantics are equivalent.
11. **No weakened Mixin validation.** Injection failure must fail loudly during development.
12. **No accidental feature redesign.** Porting is the goal; authoritative global tracking is not.

---

## 10. Known limitations intentionally retained

Because the mod remains client-observed rather than server-authoritative, this migration does not promise to track every possible world mutation.

Known product limitations may include:

- shulker movement by mechanisms the client hook does not interpret as player placement/break;
- explosion/destruction paths that do not pass through the tracked player-break event;
- changes performed by other players outside the local client's placement intent;
- command/server/plugin-driven block mutations;
- stale rows created by events the client cannot authoritatively observe.

Do not solve these by adding a server component during this port.

---

## 11. Explicitly out of scope

Do not add any of the following while porting:

- server mod requirement;
- custom packet protocol;
- cloud sync/database;
- GUI/menu rewrite;
- renderer/HUD/waypoint system;
- authoritative scanning of loaded chunks;
- datafixer/schema-version framework;
- async persistence architecture;
- new configuration framework;
- unrelated command features;
- broad code style rewrite;
- OpenGL/Vulkan work (this mod has no renderer/raw GL path).

26.2's experimental Vulkan backend is not a blocker for this mod because the audited source contains no custom rendering or raw OpenGL calls.

## 12. Risk register

| Risk | Severity | Mitigation / gate |
| --- | --- | --- |
| Yarn → official name migration obscures semantic breakage | High | migrate mappings first on 1.21.11; commit/checkpoint separately |
| `BlockItem.place` Mixin descriptor changed | High | compile + `runClient`; keep `defaultRequire=1`; successful/failed placement tests |
| Wrong placement position after context migration | High | runtime successful placement coordinate assertion |
| CSV history stranded by path change | High | preserve exact path semantics; inspect SP + MP files |
| Same XYZ cross-dimension deletion | Medium | dimension+pos identity + mandatory two-dimension test |
| State leaks across sessions | Medium | DISCONNECT cleanup + A→B smoke test |
| Destructive client command triggered from server text | Medium | `FabricClientCommandSource::attended` on every destructive literal |
| Custom name comma corrupts reload | Medium | `split(",", 7)` + `Ops, Red` restart test |
| Fabric API patch version drift | Low | pinned 0.160.0+26.2; clean dependency resolution before source work |
| Vulkan change causes regression | Low/none | no rendering code in audited source |

## 13. Strongest rejected alternative: server-authoritative tracking

A server-side rewrite could observe more block mutations and persist canonical state, but it would materially change the product:

- servers would need the mod or protocol support;
- networking and permission design would be required;
- server persistence/state migration would be introduced;
- arbitrary multiplayer compatibility would be lost.

That may be a future v2 architecture, but it is the wrong migration strategy for 26.2.

## 14. Acceptance contract

### Static/build gate

- Java 25 active;
- Gradle 9.5.1;
- target dependencies resolve;
- `./gradlew clean build` exits 0;
- no target Yarn dependency;
- no `modImplementation` target usage;
- no `ClientPlayerInteractionManagerMixin` source/config reference;
- client Mixin config is Java 25 and contains only `BlockItemMixin`;
- built jar's `fabric.mod.json` contains 26.2 / Java 25 / Fabric API metadata.

### Runtime gate

Mandatory:

1. title screen launches with no Mixin failure;
2. fresh `/shulker` empty history;
3. undyed successful placement tracked;
4. dyed successful placement tracked with correct color;
5. named `Ops, Red` placement survives disconnect/reload;
6. failed placement does not add history;
7. player break removes the correct row;
8. same XYZ in Overworld and Nether remain independent when one is broken;
9. pagination works with at least 9 entries;
10. coordinate click suggests, not runs, `/tp`;
11. `/shulker clear` preserves its existing undyed-only semantics unless explicitly changed as a separate product decision;
12. `/shulker clearall` removes all and persists;
13. existing singleplayer path is used;
14. existing multiplayer server-address path is used on a server with no server-side mod;
15. disconnect A → join B without closing Minecraft does not leak A state;
16. every destructive literal is attended and still works when typed intentionally.

## 15. Definition of done

The migration is done only when:

- the implementation follows this spec and companion implementation plan;
- Minecraft 26.2 + Fabric Loader/API launches successfully;
- clean build passes on Java 25;
- the mod remains client-only;
- only `BlockItemMixin` remains;
- all persistence and command invariants hold;
- historical CSV is readable in the original locations;
- the complete runtime smoke matrix passes;
- README accurately states 26.2 compatibility and retained limitations;
- no unrelated feature scope entered the port.
