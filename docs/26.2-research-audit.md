# Where Is My Shulker — Minecraft 26.2 Research Audit

**Status:** source audit complete; runtime gates remain for implementation  
**Research date:** 2026-09-08  
**Repository:** `Zburgers/whereismyshulker`  
**Code baseline:** `29ec55b5d8c6da614764d33da95378ec42a0d99b`

This file records **what was actually verified**, which source is authoritative for each decision, and what still requires compiler/runtime confirmation during the port. Its purpose is to stop an implementation agent from inventing APIs from memory or treating a plausible method name as a fact.

---

## 1. Research method

The migration was researched from four layers:

1. **The exact mod source** — architecture, behavior, bugs, storage format and path semantics.
2. **Official Fabric documentation** — the 26.1/26.2 toolchain boundary, Loom plugin model, Gradle/Java requirements and porting workflow.
3. **Fabric's live Maven + example project** — currently published Loader/Loom/Fabric API artifacts and canonical 26.2 build metadata.
4. **Fabric API source** — exact client command, connection lifecycle, block-break event types and callback contracts.

Vanilla Minecraft member names that remain sensitive to the exact 26.2 source must be resolved through the Loom-provided target source during implementation. The implementation plan marks those runtime/compiler gates explicitly.

Confidence labels:

- **Verified** — exact source/docs inspected.
- **Verified behavior, compile gate** — semantics and current official vocabulary are known, but the implementation must still compile against Loom's exact 26.2 source.
- **Runtime gate** — a Mixin or gameplay behavior cannot be certified by source inspection alone.

### Source footprint conclusion

The mod does **not** define:

- custom blocks/items/entities;
- registry entries;
- recipes/datagen;
- packets/protocol;
- server persistence;
- GUI/screens;
- renderer/HUD;
- raw OpenGL calls.

Therefore most 26.2 registry/rendering changes are non-applicable. The migration risk is concentrated around names/tooling, one Mixin, Fabric client APIs, and persistence identity.

## 4. Mapping migration evidence

### Finding

The source repository is on the old Yarn side of the 26.1+ naming/tooling boundary. Fabric porting guidance for projects crossing this boundary supports migrating source mappings before completing the new-version port.

Target build has no Yarn mapping dependency.

Authority:

- Fabric porting documentation: `https://docs.fabricmc.net/develop/porting/`
- Fabric mapping migration documentation under the Fabric developer docs.
- Loom docs: `https://docs.fabricmc.net/develop/loom/`

Implementation workflow:

```bash
./gradlew migrateMappings \
  --input "src/client/java" \
  --output "src/client/java" \
  --mappings "net.minecraft:mappings:1.21.11" \
  --overrideInputsIHaveABackup
```

The exact task options are still verified by running the task under the repository's Loom version before modification; the implementation plan includes a fallback documented invocation.

Confidence: **Verified workflow; command-shape compile/tool gate**.

Why this matters: an automatic name conversion and a 26.2 semantic change should not be mixed into one opaque diff.

## 5. Fabric client block-break event

### Exact source

`ClientPlayerBlockBreakEvents` exists at:

```text
net.fabricmc.fabric.api.event.client.player.ClientPlayerBlockBreakEvents
```

Fabric API source inspected:

`https://github.com/FabricMC/fabric-api/blob/7984737f42c8e8a36f4f880014e952a76cbefcdb/fabric-events-interaction-v0/src/client/java/net/fabricmc/fabric/api/event/client/player/ClientPlayerBlockBreakEvents.java`

### Exact callback

```java
void afterBlockBreak(
    ClientLevel level,
    LocalPlayer player,
    BlockPos pos,
    BlockState state
)
```

The source explicitly describes `state` as the block state **before** the block was successfully broken.

Fabric's own client break instrumentation invokes this AFTER event with the saved old state after the block-break method succeeds.

### Migration decision

Delete `ClientPlayerInteractionManagerMixin` and use:

```java
ClientPlayerBlockBreakEvents.AFTER.register((level, player, pos, state) -> {
    if (state.getBlock() instanceof ShulkerBoxBlock) {
        ShulkerBoxTracker.getInstance().onShulkerBoxBroken(pos, level);
    }
});
```

Confidence: **Verified**.

This is stronger than merely porting the old Mixin because it removes a version-sensitive bytecode hook while preserving the semantics the mod needs.

## 6. Fabric client connection lifecycle

### Exact source

`ClientPlayConnectionEvents`:

`https://github.com/FabricMC/fabric-api/blob/7984737f42c8e8a36f4f880014e952a76cbefcdb/fabric-networking-api-v1/src/client/java/net/fabricmc/fabric/api/client/networking/v1/ClientPlayConnectionEvents.java`

### Verified callbacks

JOIN:

```java
void onPlayReady(
    ClientPacketListener listener,
    PacketSender sender,
    Minecraft client
)
```

DISCONNECT:

```java
void onPlayDisconnect(
    ClientPacketListener listener,
    Minecraft client
)
```

### Migration decision

- JOIN resolves storage + loads CSV.
- DISCONNECT clears in-memory rows + path.

Confidence: **Verified**.

Why this fixes a real bug: the existing code clears on whole-client stopping. A user can disconnect from server/world A and enter B in the same Minecraft process, so shutdown is the wrong session boundary.

## 7. Fabric client command source and attendance

### Exact source

`FabricClientCommandSource`:

`https://github.com/FabricMC/fabric-api/blob/7984737f42c8e8a36f4f880014e952a76cbefcdb/fabric-command-api-v2/src/client/java/net/fabricmc/fabric/api/client/command/v2/FabricClientCommandSource.java`

`ClientCommands`:

`https://github.com/FabricMC/fabric-api/blob/7984737f42c8e8a36f4f880014e952a76cbefcdb/fabric-command-api-v2/src/client/java/net/fabricmc/fabric/api/client/command/v2/ClientCommands.java`

### Verified members

`FabricClientCommandSource` exposes:

```text
sendFeedback(Component)
sendError(Component)
getClient()
getPlayer()
getLevel()
attended()
```

The API documentation says destructive or privileged client commands should require `attended()`, specifically because server-provided text can otherwise initiate client commands without direct user intent.

### Migration decision

Use:

```java
.requires(FabricClientCommandSource::attended)
```

on:

- `clear`;
- `clearall`;
- any retained reset/prune destructive aliases.

Do not put it on root/page navigation.

Confidence: **Verified**.

## 8. Command tree decision

Current command handling treats the argument as a string and performs fuzzy prefix checks.

Target:

```text
/shulker
/shulker <page:int>=1
/shulker clear
/shulker clearall
```

Optional compatibility literals:

```text
reset
resetall
prune
pruneall
```

No fuzzy prefix behavior remains.

Reasoning:

- Brigadier should own type validation;
- commands become discoverable/predictable;
- destructive branches can be independently gated as attended;
- page rendering no longer has parsing exceptions mixed with destructive behavior.

Confidence: **Architecture decision based on verified Fabric API**.

## 9. Placement Mixin audit

### Why the Mixin remains

The placement hook needs two coupled facts:

1. a snapshot of the source `ItemStack` custom name before placement mutates/decrements the stack;
2. confirmation after vanilla returns that placement actually succeeded and resulted in a shulker at the target position.

The audited Fabric APIs provide a clean replacement for the break hook, but no reviewed high-level Fabric event was found that provides this exact placement transaction with the source-stack timing and final success semantics required by the current product.

Therefore the smallest reliable design keeps one Mixin.

### Target official concepts

Current 26.2 vocabulary researched for the port:

```text
BlockItem
BlockPlaceContext
InteractionResult
Level
BlockPos
BlockState
ShulkerBoxBlock
ItemStack
Component
```

Expected target method:

```java
InteractionResult BlockItem.place(BlockPlaceContext)
```

Expected success predicate:

```java
result.consumesAction()
```

Expected source-name path:

```java
context.getItemInHand().getCustomName()
```

Expected target-position path:

```java
context.getClickedPos()
```

### Confidence boundary

- public vanilla vocabulary/semantics: **Verified behavior, compile gate**;
- exact Mixin descriptor/injection match: **Runtime gate**;
- placement position correctness for all normal shulker placements: **Runtime gate**.

The implementation must inspect Loom's exact 26.2 `BlockItem` source and launch a client. A compile success alone is not enough.

### Mandatory Mixin policy

Keep:

```json
"injectors": {
  "defaultRequire": 1
}
```

Never suppress a target failure.

## 11. Dimension identity audit

### Current bug

`onShulkerBoxBroken(BlockPos pos)` removes rows by coordinate only.

This means:

```text
minecraft:overworld @ x/y/z
minecraft:the_nether @ x/y/z
```

collide.

### Target identity

Use:

```text
dimension resource id + BlockPos
```

Expected 26.2 official shape:

```java
level.dimension().identifier().toString()
```

Historical row values already look like:

```text
minecraft:overworld
minecraft:the_nether
minecraft:the_end
```

Confidence: **Verified behavior, compile gate for exact vanilla member spelling**.

Mandatory gameplay gate: place two boxes at the same XYZ in different dimensions and break only one.

## 12. Shulker color audit

### Current behavior

Color is reverse-engineered from a translation key, then title-cased.

### Target behavior

Use the shulker block's color API:

```text
ShulkerBoxBlock.getColor() -> nullable DyeColor
```

Then use the dye's serialized name to produce the existing display convention.

Examples:

```text
null       -> ""
red        -> "Red"
light_blue -> "Light Blue"
```

Confidence: **Verified behavior, compile gate for exact vanilla member access**.

Why not store `light_blue` directly? Existing rows already use human-readable values. Keeping the old convention avoids a needless mixed-data presentation change.

## 13. CSV compatibility audit

Current parser:

```java
csvLine.split(",")
```

Known failing row concept:

```text
10,64,20,minecraft:overworld,Red,123456789,Ops, Red
```

Unbounded split yields too many fields and the parser rejects the row.

Target:

```java
csvLine.split(",", 7)
```

Because customName is the final field, this preserves commas there without changing the existing row schema.

Continue accepting 6-column historical rows.

Confidence: **Verified from repository code / Java semantics**.

Mandatory regression: `Ops, Red` survives reload.

## 17. Things deliberately not claimed as source-certified

The docs do **not** claim the following can be proven before implementation runtime:

1. that the new `BlockItemMixin` descriptor will apply successfully on the first attempt;
2. that every constructor overload for click/hover events is exactly as sketched in planning prose;
3. that a particular internal vanilla field is preferable to a public accessor where both exist;
4. that the multiplayer server address API behaves identically in every launch mode without a smoke test;
5. that every vanilla placement edge case uses the expected contextual position without testing.

These are why the plan has compiler and runtime gates rather than hiding uncertainty behind guessed code.

## 18. Research conclusions

### High-confidence migrations

- build/toolchain lock;
- non-remapping Loom model;
- Java 25;
- remove Yarn target dependency;
- break event replacement;
- disconnect lifecycle replacement;
- client command vocabulary;
- destructive-command attendance;
- Mixin config Java 25;
- CSV comma fix;
- dimension+position identity requirement;
- dead scaffolding removal;
- Vulkan non-applicability.

### Runtime-sensitive migration

One integration point remains intentionally low-level:

```text
BlockItem placement Mixin
```

This is the highest-risk part of the port and receives the strongest runtime gate.

### Overall port complexity

**Moderate, bounded.** The Minecraft/Fabric generation jump is large, but the mod itself has a narrow surface area. If the implementation follows the staged name migration and keeps the placement Mixin isolated, most failures should be ordinary compiler/API resolution rather than architectural redesign.
